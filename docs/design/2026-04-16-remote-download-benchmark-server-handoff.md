# Remote Download Benchmark Server Handoff

> Date: 2026-04-16
> Status: Active handoff note
> Scope: backend/server-side implementation needed to unblock `tool/rhttp_download_bench.dart --base-url=...`

## 1. Why This Exists

`flutter_rust_net` already has a standalone download benchmark that compares
`dio` and `rhttp` on download-to-file workloads.

Local loopback validation is already in place, but the current fixed public
remote base URL `http://47.110.52.208:7777` does not expose a compatible
`/bench/download-file` endpoint yet. As a result, remote smoke validation is
still blocked.

This document is the server-side handoff note for the agent or engineer who
will implement the remote endpoint.

## 2. Deliverable

Add one remote-compatible benchmark endpoint:

```text
GET {baseUrl}/bench/download-file
```

The endpoint must be compatible with the existing repository benchmark client
without requiring any client-side code changes.

## 3. Current Blocker

Today the repository is in a "core implementation complete, validation closing"
phase. The main blocker is not the client benchmark code itself, but the lack
of a compatible remote endpoint.

Current known symptom:

```text
GET http://47.110.52.208:7777/bench/download-file?bytes=32&chunkBytes=8&chunkDelayMs=0
=> 404 Not Found
```

Until this endpoint exists, `--base-url=...` runs cannot produce reliable
remote comparison evidence for `dio` and `rhttp`.

## 4. Required Request Contract

Request path:

```text
/bench/download-file
```

Request method:

```text
GET
```

Required query parameters:

- `bytes`: total response size in bytes
- `chunkBytes`: intended server-side chunk size
- `chunkDelayMs`: intended delay between chunks in milliseconds

Example:

```text
GET https://bench.example.com/api/bench/download-file?bytes=131072&chunkBytes=65536&chunkDelayMs=0
```

Important client assumptions:

- the benchmark client always appends `/bench/download-file`
- the benchmark client does not send a request body
- the benchmark client does not send auth tokens or custom benchmark headers
- `baseUrl` is treated as a clean base URL and the fixed path is appended by the
  client

If the deployment requires auth or custom headers later, the client must be
extended explicitly. That is out of scope for this handoff.

## 5. Required Response Contract

The endpoint must return a successful `2xx` response only when it can produce a
fully compatible payload.

Compatibility rules:

1. response status is `2xx`
2. response body length is exactly `bytes`
3. payload bytes follow the deterministic rule below
4. the downloaded file produced by the client must match the expected checksum

Deterministic payload rule:

```text
byte[i] = (i * 31 + 17) % 251
```

Equivalent pseudocode:

```text
for i in 0..bytes-1:
  output ((i * 31 + 17) % 251)
```

Recommended response headers:

- `Content-Type: application/octet-stream`
- `Content-Length: {bytes}`

Recommended transport behavior:

- stream in chunks close to `chunkBytes`
- if `chunkDelayMs > 0`, wait about that many milliseconds between chunks

## 6. Checksum Rule Used By The Client

The remote endpoint does not need to return a checksum field, but the response
payload must satisfy the same checksum calculation as the local reference
server.

Client-side checksum algorithm:

```text
checksum = 0
for each byte:
  checksum = ((checksum * 33) + byte) & 0x7fffffff
```

The benchmark counts a run as successful only when status, final file size, and
checksum all match expectations.

## 7. Recommended Server Behavior

The simplest compatible implementation is:

1. parse `bytes`, `chunkBytes`, and `chunkDelayMs`
2. validate they are integers and not negative
3. stream exactly `bytes` bytes generated by the deterministic rule
4. write data in chunks of about `chunkBytes`
5. optionally sleep between chunks when `chunkDelayMs > 0`
6. set `Content-Length` when possible

Recommended invalid-input behavior:

- return `400 Bad Request` for malformed or negative query values
- keep the response body simple; a short text error is enough

This is acceptable because the benchmark client sends valid values during
normal operation.

## 8. Framework-Agnostic Pseudocode

```text
read bytes, chunkBytes, chunkDelayMs from query
if any value is invalid:
  return 400

set status = 200
set content-type = application/octet-stream
set content-length = bytes

for offset in 0..bytes step chunkBytes:
  end = min(offset + chunkBytes, bytes)
  chunk = new byte[end - offset]
  for i in offset..end-1:
    chunk[i - offset] = (i * 31 + 17) % 251
  write chunk to response stream
  flush if needed
  if chunkDelayMs > 0 and end < bytes:
    sleep chunkDelayMs

close response
```

## 9. Acceptance Criteria

Server-side implementation is considered ready when all of the following are
true:

1. `GET /bench/download-file` returns `2xx`
2. `Content-Length` equals the requested `bytes`
3. the actual response body length equals `bytes`
4. the payload follows `(i * 31 + 17) % 251`
5. the repository benchmark can run against the remote URL without client
   changes
6. a remote smoke run can produce a JSON report for at least the `dio` channel
7. if local `librhttp.dylib` is configured correctly, the same remote smoke run
   can also complete for the `rhttp` channel

## 10. Suggested Validation Steps

Basic endpoint probe:

```bash
curl -sS -D - \
  'http://47.110.52.208:7777/bench/download-file?bytes=32&chunkBytes=8&chunkDelayMs=0' \
  -o /tmp/flutter_rust_net_remote_download_probe.bin
```

Repository minimum smoke command (`dio` only, no local `rhttp` native library required):

```bash
dart run tool/rhttp_download_bench.dart \
  --base-url=http://47.110.52.208:7777 \
  --channels=dio \
  --requests=1 \
  --warmup=0 \
  --file-bytes=131072 \
  --verbose=false \
  --output=build/rhttp_download_remote_smoke_dio.json
```

Repository dual-channel smoke command (requires local `librhttp.dylib` setup):

```bash
FRB_DART_LOAD_EXTERNAL_LIBRARY_NATIVE_LIB_DIR="/absolute/path/to/rhttp/rust/target/release" \
dart run tool/rhttp_download_bench.dart \
  --base-url=http://47.110.52.208:7777 \
  --channels=dio,rhttp \
  --requests=1 \
  --warmup=0 \
  --file-bytes=131072 \
  --verbose=false \
  --output=build/rhttp_download_remote_smoke.json
```

Expected result:

- endpoint probe no longer returns `404`
- `build/rhttp_download_remote_smoke_dio.json` includes successful `dio` results
- benchmark JSON includes successful `rhttp` results when the local native
  library is configured correctly

## 11. Non-Goals

This handoff does not require:

- upload endpoint changes
- auth support for the benchmark client
- resume / cancel / progress parity work
- business API integration
- persistent file storage
- CDN optimization
- new client-side benchmark arguments

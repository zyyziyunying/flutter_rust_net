# Remote Download Benchmark Endpoint Contract

> Date: 2026-04-08
> Status: Active design note
> Scope: remote endpoint contract required by `tool/rhttp_download_bench.dart --base-url=...`

## 1. Background

`flutter_rust_net` now has a standalone download benchmark that compares `dio`
and `rhttp` on download-to-file workloads.

When `--base-url` is provided, the benchmark does not accept an arbitrary file
URL. It assumes the remote server implements the same benchmark endpoint
contract as the local scenario server.

This note records the exact remote compatibility requirements so a server-side
test endpoint can be prepared without guessing from tool output.

## 2. Fixed Request Shape

The benchmark treats `baseUrl` as a base address and always appends the same
path:

```text
{baseUrl}/bench/download-file
```

The request method is always:

```text
GET
```

The current CLI does not send:

- request body
- auth token
- custom benchmark headers
- signed query fields beyond the benchmark parameters

If auth or custom headers are required in the future, the benchmark client must
be extended explicitly. The current remote endpoint should therefore be exposed
as a simple unauthenticated or already-network-allowlisted test endpoint.

## 3. Required Query Parameters

The benchmark currently sends these query parameters:

- `bytes`: target response size in bytes
- `chunkBytes`: intended server-side chunk size
- `chunkDelayMs`: intended per-chunk delay in milliseconds

Example:

```text
GET https://bench.example.com/api/bench/download-file?bytes=131072&chunkBytes=65536&chunkDelayMs=0
```

## 4. Required Response Conditions

The benchmark marks an attempt as successful only when all of the following are
true:

1. HTTP status code is `2xx`
2. the downloaded file size exactly equals `bytes`
3. the file checksum matches the expected deterministic payload

This means a remote server is compatible only if it returns a deterministic
payload that matches the repository's local benchmark payload generator.

## 5. Deterministic Payload Contract

For byte index `i` starting from `0`, the response byte must be:

```text
byte[i] = (i * 31 + 17) % 251
```

The response body must contain exactly `bytes` bytes generated by that rule.

Equivalent pseudocode:

```text
for i in 0..bytes-1:
  output ((i * 31 + 17) % 251)
```

## 6. Checksum Contract

The benchmark validates the downloaded file with this rolling checksum:

```text
checksum = 0
for each byte:
  checksum = ((checksum * 33) + byte) & 0x7fffffff
```

The remote endpoint does not need to return the checksum in headers or body,
but the payload it returns must produce the same checksum as the local
generator.

## 7. Response Header Guidance

The benchmark currently relies on final file bytes, not on response headers for
correctness, but a compatible endpoint should still return:

- `Content-Type: application/octet-stream`
- `Content-Length: {bytes}`

The local reference server also returns `200 OK` plus `Content-Length` equal to
the requested byte size.

## 8. Chunking And Delay Semantics

For strongest compatibility with the local scenario server, the remote endpoint
should:

- stream the response in chunks of roughly `chunkBytes`
- wait about `chunkDelayMs` milliseconds between chunks when `chunkDelayMs > 0`

These two parameters are mainly used to shape delivery behavior for the
benchmark. The current client ultimately validates final status, file size, and
checksum. Even so, mirroring the local chunking behavior is recommended so
remote runs remain comparable to local runs.

## 9. Base URL Constraints

The benchmark's `baseUrl` must be:

- an absolute `http://` or `https://` URL
- free of query string and fragment

Trailing `/` is tolerated by the client and is normalized away before the fixed
path is appended.

## 10. Reference Behavior In This Repository

The exact client/server contract is currently implemented in:

- `lib/network/benchmark/download_benchmark_support.dart`
- `lib/network/benchmark/download_benchmark_harness.dart`
- `lib/network/benchmark/benchmark_scenario_server.dart`

The important repository behaviors are:

- request URL assembly: append `/bench/download-file` and benchmark query params
- success rule: `2xx` + exact file size + expected checksum
- local reference endpoint: deterministic binary stream with configurable chunk
  size and per-chunk delay

## 11. Server Checklist

Before handing a remote URL to the benchmark, confirm the server endpoint:

1. exposes `GET /bench/download-file`
2. accepts `bytes`, `chunkBytes`, and `chunkDelayMs`
3. returns exactly `bytes` bytes
4. generates bytes with `(i * 31 + 17) % 251`
5. returns a `2xx` status
6. preferably sets `Content-Length`
7. preferably streams using `chunkBytes` and `chunkDelayMs`

## 12. Example Validation Command

Once a compatible endpoint exists, run the remote smoke command with
`FRB_DART_LOAD_EXTERNAL_LIBRARY_NATIVE_LIB_DIR` set to the local directory
that contains `librhttp.dylib`:

```bash
FRB_DART_LOAD_EXTERNAL_LIBRARY_NATIVE_LIB_DIR="/absolute/path/to/rhttp/rust/target/release" \
dart run tool/rhttp_download_bench.dart \
  --base-url=https://bench.example.com/api \
  --channels=dio,rhttp \
  --requests=1 \
  --warmup=0 \
  --file-bytes=131072 \
  --verbose=false \
  --output=build/rhttp_download_remote_smoke.json
```

The exact native-library path is machine-specific and may differ across pub
cache hosts, dependency versions, or local build layouts.

If the endpoint is compatible and
`FRB_DART_LOAD_EXTERNAL_LIBRARY_NATIVE_LIB_DIR` points to a directory
containing `librhttp.dylib`, the output JSON should contain both `dio` and
`rhttp` channel results without failures. If the endpoint is compatible but the
local `rhttp` native library is unavailable or the environment variable is
unset/misconfigured, expect the run to record `dio` only and report `rhttp`
under `skippedChannels`.
